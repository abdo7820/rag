# Liver Diseases RAG

Hybrid retrieval-augmented Q&A over a single hepatology research paper —
*"Liver diseases: epidemiology, causes, trends and predictions"*
(Gan et al., 2025, doi:10.1038/s41392-024-02072-z).

Semantic search + BM25 + a Neo4j knowledge graph feed a 6-step, cited,
self-verifying answer chain. All tunables live in one place: `config.py`.

## Architecture

```
Query ──► Semantic (Chroma) ──┐
      └─► BM25 ────────────────┼─► RRF fusion ─► Cross-encoder rerank ─┐
      └─► Neo4j graph lookup ──┼───────────────────────────────────────┼─► Answer
                                                                        │
                        (6-step chain: guardrail → rewrite → retrieve →
                         scope check → draft → verify)
```

See `dashboard.html` for a live, interactive view of this — health status,
a fast/strong/full-answer console, a graph explorer, and the evaluation
numbers below, all in one page.

## Project layout

```
config.py              # single source of truth for every path/param/model name
app.py                  # FastAPI wrapper (GET /health, POST /search, POST /ask, GET /graph/{entity})
dashboard.html           # standalone frontend — open directly in a browser
Procfile / requirements.txt   # Railway/production deploy

rag/
  pdf_to_markdown.py    # 1. PDF -> Markdown
  chunker.py             # 2. Markdown -> chunks.json
  embed.py                # 3a. chunks.json -> embeddings.npy
  store.py                 # 3b. embeddings.npy -> Chroma vectorDB/
  bm25_index.py             # 3c. chunks.json -> BM25 index
  test_search.py             # hybrid retrieval (semantic+BM25+RRF+rerank), used by app.py & generate.py
  generate.py                 # the 6-step grounded-answer chain

models/
  extract_graph.py       # 4a. chunks.json -> graph_triples.json (LLM extraction)
  load_graph.py            # 4b. graph_triples.json -> Neo4j
  query_graph.py             # CLI sanity check for the graph

eval/
  qa_dataset.json         # 27-question benchmark
  evaluate_retrieval.py    # Hit Rate@K, Precision@K, MRR, latency, failure analysis

data/                      # generated artifacts land here (chunks.json, embeddings, bm25 index, graph triples)
vectorDB/                   # generated by rag/store.py
```

## Setup

```bash
pip install -r requirements.txt
cp .env.example .env   # fill in GROQ_API_KEY and (optionally) NEO4J_*
```

Place the source PDF at `data/s41392-024-02072-z.pdf`, then run the pipeline
in order:

```bash
python rag/pdf_to_markdown.py
python rag/chunker.py
python rag/embed.py
python rag/store.py
python rag/bm25_index.py

# optional — knowledge graph
python models/extract_graph.py
python models/load_graph.py
```

## Run

```bash
uvicorn app:app --reload --port 8000
```

Open `dashboard.html` in a browser (same machine — it calls
`http://127.0.0.1:8000` by default, editable in the top bar).

## Evaluate

```bash
python eval/evaluate_retrieval.py
```

Reports Hit Rate@5, avg Precision@5, MRR, and latency for RRF-only vs.
RRF+reranked, plus a per-question failure analysis with likely cause. Full
report saved to `eval/results.json`.

Latest snapshot (27 questions, top_k=5):

| Metric | RRF only | + Rerank |
|---|---|---|
| Hit Rate@5 | 0.926 | **1.000** |
| Avg Precision@5 | 0.548 | 0.570 |
| MRR | 0.859 | 0.901 |
| Avg latency | 0.147s | 1.038s |

## Deploy (Railway)

**Free tier (≈512MB RAM) — use the Hugging Face Inference API path:**

1. Push this folder to a repo, connect it on Railway.
2. In Settings, set the **Build Command** to `pip install -r requirements-railway.txt` (skips torch — the single biggest cause of free-tier OOM).
3. Set variables: `GROQ_API_KEY`, `ENVIRONMENT=production`, `USE_HF_INFERENCE_API=true`, `HF_API_TOKEN=<your token from https://huggingface.co/settings/tokens>`. `NEO4J_*` optional.
4. Still run `rag/embed.py` + `rag/store.py` **locally first** (with the full `requirements.txt`, which does need torch) to build `vectorDB/` and `data/embeddings.npy` — only commit/upload the resulting `data/` and `vectorDB/` folders, not the model-loading step itself.
5. `Procfile` handles the rest — single worker, binds to `$PORT`.

This keeps retrieval quality identical (same model weights — `BAAI/bge-large-en-v1.5` and `cross-encoder/ms-marco-MiniLM-L-6-v2` — just running on Hugging Face's servers instead of Railway's RAM) while cutting this app's own memory footprint to roughly what FastAPI + chromadb + the BM25 pickle need (~100-150MB).

**Paid tier with enough RAM (1.5GB+) — skip the API and run everything locally:**

1. Use `requirements.txt` (includes torch) as the Build Command target, leave `USE_HF_INFERENCE_API=false` (or unset).
2. If RAM is still tight, `EMBED_MODEL_NAME=BAAI/bge-base-en-v1.5` trades some retrieval quality for ~1GB less RAM — rebuild `vectorDB/` with `embed.py` + `store.py` after switching, since embedding dimensions differ from bge-large.
3. `Procfile` handles the rest — single worker, binds to `$PORT`. Don't add extra workers; each one loads its own full copy of the models.

## Known trade-offs / design notes

- **RRF_TOP_K vs EVAL_RRF_TOP_K** (`config.py`): production keeps a narrower
  candidate pool (8) than the eval script stress-tests (20) — documented
  explicitly so the eval numbers above aren't mistaken for exactly what
  `/search` returns live.
- **Graph entity matching** uses word-boundary regex, not substring
  `CONTAINS` — avoids short entity names (e.g. "AST") false-matching inside
  unrelated words.
- **Guardrail** (`rag/generate.py`) is a keyword heuristic, not a clinical
  safety system — it can both over-block ("what's a typical HBV antiviral
  dosage" is a legitimate informational question) and under-block a
  cleverly-phrased personal question. Acceptable for a research-paper Q&A
  demo; would need an LLM-based classifier layer for a real clinical
  deployment.
